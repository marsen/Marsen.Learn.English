# 覆蓋上傳：同一套題重新上傳時怎麼判斷

同一個 `set_id` 再上傳時，網站不會直接擋掉，也不會直接蓋掉：先拿新的 set.json 跟資料庫裡那份比對，告訴管理員「覆蓋會怎樣」，**按了按鈕才寫入**。

最常見的用途：把當初用 2.0 打包（沒有逐字稿）的題組，用 Question.Generator 重新打包成 2.1，覆蓋上傳補上逐字稿。

- 判斷：`src/domain/examSet/overwrite.ts`（`checkOverwrite`，測試在同一層）
- 流程：`src/application/examSet/uploadExamSet.ts`
- 畫面：`/admin/sets/upload`（`src/presentation/components/admin/BatchUploadForm.tsx`）

## set.json 的欄位怎麼分

set.json 最上層有 12 個欄位，分成三類：

| set.json 欄位 | 內容 | 歸類 | 內容的分類 |
|---|---|---|---|
| `title` | 標題 | 內容 | 標題 |
| `topic` | 主題 | 內容 | 標題 |
| `question_count` | 題數 | 內容 | 題目卷 |
| `paper` | 題目卷（所有列、空格） | 內容 | 題目卷 |
| `answers` | 答案卡（正解、也算對的寫法、批改規則、陷阱…） | 內容 | 答案 |
| `timing` | 錄音時間軸 | 內容 | 錄音 |
| `audio` | 錄音的檔名、大小、sha256、秒數 | 內容 | 錄音 |
| `transcript` | 逐字稿、每題答案的出處（2.1 起） | 補充資料 | — |
| `provenance` | 製作紀錄（AI 審稿結論、示警…） | 補充資料 | — |
| `schema_minor` | 小版號（0＝2.0、1＝2.1） | 補充資料 | — |
| `schema_version` | 大版號 | 不比 | 網站只收 2，一定一樣 |
| `set_id` | 題組代號 | 不比 | 就是用它找出網站上那一份 |

- **內容**：考生看到、聽到、被批改的東西。不同就要重新審稿。
- **補充資料**：給老師審稿、給管理員看的東西，不影響考試本身。
- 7 個內容欄位分成 4 類（標題、題目卷、答案、錄音）。程式會記下是哪幾類不同（`fields`），畫面目前不顯示。

## 怎麼比

是整包比，不是一個欄位一個欄位比：

- `paper`、`answers`、`timing`、`transcript`、`provenance` 都是一整個 JSON，各用一次 `sameJson` 比完。之後 set.json 在這些欄位**裡面**加東西，會自動被比到，不用改程式。
- 錄音不比檔案內容，比的是儲存位置（`audioKey`）裡的 sha256 前 8 碼：`<set_id>/audio-<前 8 碼>.mp3`。錄音的大小和 sha256 在上傳時就已經驗證過跟檔案一致。
- `sameJson` 會先把物件的鍵排序再比，因為 Postgres 的 jsonb 存進去再讀出來，鍵的順序會變，直接 `JSON.stringify` 比會把一樣的判成不同。陣列的順序要一樣（題目、答案的順序本來就有意義）。

## 三種結果

依序判斷：

1. 內容欄位有任何一個不同 → **內容有變**（`content`）
2. 內容都一樣、補充資料有不同 → **只補資料**（`supplement`）
3. 全部一樣 → **完全一樣**（`unchanged`）

| 結果 | 畫面 | 按下去之後 |
|---|---|---|
| 內容有變 | 「內容不同，覆蓋後要重新審稿」＋紅色的「覆蓋」 | 整套換掉；狀態退回**待審**（開放對象保留，老師重新通過前考不到）；目前的審稿意見清掉，「審稿紀錄」的歷史保留；錄音換了就另存新檔，舊檔留著 |
| 只補資料 | 「內容相同，覆蓋後審核狀態不變」＋「覆蓋」 | 只更新逐字稿、製作紀錄、AI 結論、版本；審核狀態、開放對象、老師意見都不動 |
| 完全一樣 | 「內容相同，不用上傳」 | 沒有按鈕，什麼都不動 |

沒按按鈕，網站上維持原本那份。按鈕用詞：新的題組是「上傳」，網站上已經有的是「覆蓋」。

## 對考試紀錄的影響

- **已經交卷的**：不受影響。交卷時就把分數、每題的作答、對錯和當時的正解一起存了（`exam_attempts.results`），覆蓋後不會重新批改。
- **正在考、還沒交卷的**：交卷時用的是**當下**網站上的答案卡。如果剛好在他考試中覆蓋了答案，他會用新答案批改。目前題組在內容有變時會退回待審、新的人考不到，這種重疊很少見，所以先不處理；之後做「封存題組」時再一起考慮（見 `docs/roadmap.md`）。

## 版本顯示

- `exam_sets.schema_minor`（migration `0014`）：既有的題組依有沒有逐字稿回填 2.0／2.1
- 題組清單的「版本」欄：2.0 灰色、2.1 綠色

## 補逐字稿的步驟（2.0 → 2.1）

1. Question.Generator：主題庫改過的話，舊題組會被判定「過期」而不能打包，要先認可再打包
   ```bash
   uv run python -m src accept results/sets/<set_id>
   uv run python -m src bundle results/sets/<set_id>
   ```
2. 網站 `/admin/sets/upload` 選 `results/out`（或其中一套），按「上傳」
3. 出現「內容相同，覆蓋後審核狀態不變」就按「覆蓋」；出現「內容不同」代表重新打包後題目、答案或錄音跟網站上的不一樣，要先確認原因再決定要不要覆蓋

## 之後可能的改進（還沒做）

- 審稿意見的歷史版本與差異比對：每次覆蓋存一個版本，審稿記下是針對哪一版（`docs/roadmap.md` 的「題組管理」）
- 改用內容指紋：上傳時把內容欄位算成一個 hash 存起來，比對時只比一個值。程式更短，但就說不出是哪一類不同
